## Resumen ejecutivo

**Estado del código: estable. Estado de producción: 1 bug CRÍTICO en el bootstrap del AuthProvider.**

El proyecto está en excelente forma técnicamente: tsc verde, vite build verde, bundle inicial 480 KB / 141 KB gzip (dentro del target 500/145), 0 secretos en el repo, 0 usos de `any`, 0 imports relativos con `../..`. La fase 19-0 se aplicó limpiamente con migración idempotente y cero mutaciones a datos existentes.

**Pero hay un bug crítico que bloquea el uso de la app en producción**: `supabase.auth.getSession()` no resuelve la Promise (nunca `.then`, nunca `.catch`), lo que causaba el splash `Cargando…` eterno. El fix defensivo del commit `b7ff827` (timeout 8s + `.finally`) lo mitiga — la app ya no se cuelga forever — pero deja al usuario en un estado degradado: `session=null` → `profile=null` → **"No hay perfil cargado"**, exactamente lo que se ve ahora. El root cause aún no está fijado.

Los warnings de `contentscript.js:14083` en Console indican que hay una extensión de navegador (probablemente MetaMask/wallet crypto) inyectando código con múltiples EventEmitters (11+ listeners), lo que puede estar saturando el event loop y causando que las Promises de `supabase-js` nunca resuelvan. El usuario confirmó que el bug pasa en varias computadoras, así que la extensión NO es la causa raíz — es un problema estructural del bootstrap.

## Findings

### 🔴 CRITICAL — bloquean producción

#### C-1 · `supabase.auth.getSession()` cuelga forever · [D4]

**Evidencia:**
- Console log del user: `[auth] bootstrap timeout after 8s — forcing loading=false. Session may be null.`
- Pantalla resultante: **"No hay perfil cargado"** ([`src/modules/dashboard/DashboardPage.tsx:15`](src/modules/dashboard/DashboardPage.tsx))
- Reproduce en varias computadoras (no es cache ni extensión)
- Session válida existe en localStorage (confirmado por el user)
- Cero requests a `supabase.co` durante el bootstrap (confirmado por `performance.getEntriesByType('resource')`)

**Cadena de fallo:**
1. `AuthProvider` monta en `src/lib/auth.tsx`
2. Llama `supabase.auth.getSession()` — esta Promise **nunca resuelve ni rechaza**
3. Sin el fix (pre-`b7ff827`): `setLoading(false)` nunca corre → splash "Cargando…" eterno
4. Con el fix (post-`b7ff827`): timeout de 8s dispara `setLoading(false)` → `session=null` → `profile=null` → pantalla "No hay perfil cargado"

**Root cause probable:**
`supabase-js` lee el token de `localStorage` y no hace fetch, pero internamente espera un evento (`onAuthStateChange` de tipo `INITIAL_SESSION`) que en presencia de ciertos content-scripts (MetaMask, extensiones que monkey-patchean `window.postMessage`) NUNCA se dispara. La Promise queda pending forever.

**Impacto:** La app es inutilizable en producción. Con el fix defensivo, cargas pero sin perfil = sin acceso a nada.

**Fix propuesto (siguiente commit):**

Opción A · **Bypass del bootstrap con `getUser()`** — hace fetch a la API en vez de esperar el evento:

```typescript
// src/lib/auth.tsx — reemplazar el getSession() del bootstrap
supabase.auth.getUser()   // ← hace fetch a /auth/v1/user, no espera evento local
  .then(async ({ data }) => {
    if (data.user) {
      const p = await loadProfile(data.user.id);
      if (mounted) {
        setSession({ user: data.user } as Session);   // reconstruir session básico
        setProfile(p);
      }
    }
  })
  .finally(() => setLoading(false));
```

Opción B · **Invalidar auth token corrupto y forzar re-login** — más agresivo pero garantizado:

```typescript
// Detectar bootstrap failure y limpiar localStorage
if (bootstrapTimedOut) {
  localStorage.removeItem('sb-bbxieuyhzxqygkkxwvwo-auth-token');
  navigate('/login', { replace: true });
}
```

**Priority: inmediata.** Sin este fix, la app está caída en producción para todos los usuarios.

## Riesgos monitoreados (no findings pero worth watching)

1. **Bundle a 141 KB gzip / 145 KB target** — a 3% del límite. Cualquier librería nueva grande (moment, jQuery, etc.) rompería el target. `xlsx` (SheetJS) ya es lazy, no cuenta.
2. **`audit_log` sin particionamiento** — con `audit_trigger` en 13 tablas nuevas (F19-0) + 6 tablas financieras + Vehículos (fase 18) = 20 tablas escribiendo a `audit_log`. Riesgo baja: volumen de negocio muy bajo. Si en 6 meses `audit_log` > 100k filas, considerar particionado por mes.
3. **`att_pins` deprecada desde fase 8 pero aún RLS + trigger** — no molesta pero es ruido. Puede droppearse en una migración futura.
4. **Cliente Supabase inicializa con `placeholder.supabase.co` si env vars faltan** — [`src/lib/supabase.ts:15-19`](src/lib/supabase.ts). Correcto para desarrollo, pero si Vercel un día no tiene las vars, la app arrancaría contra URL falsa. Ya verificamos que actualmente están OK.
